# peer-agents 线协议 v1

> 一页纸的规范。照着它，任何语言都能写一个接进这套系统的 Agent。

## 0. 这份协议解决什么问题

在这份协议之前，README 里说的「Agent 之间的通信」，其实是**进程内的对象传递**：
把同一个 Python 对象塞进另一个 Python 列表。

可这个项目研究的是 *通信*。而进程内传递恰恰是通信问题里最简单的那一档 ——
没有序列化、没有半包、没有对端消失、没有版本不一致。

边界一旦挪到线上，这四件事会一起出现。

## 1. 立场：远端就是一个「你不拥有的大脑」

这是整个协议的立足点，也是它和「把总线搬到网络上」最大的区别。

远端进程：

- **不接入总线**，**不碰拓扑**，**不写黑板**；
- 只实现一件事 —— 看着自己的信箱，说出自己想发什么。

于是它继承的权限和 `LLMBrain` **完全一样**，一行都不用放宽：

| 它可以 | 它不可以 |
|---|---|
| 决定跟谁说话（`to`） | 决定自己**是谁**（`sender` 由宿主按会话身份填） |
| 决定说什么类型（数据面 `kind`） | 发控制面报文（`LINK_REQUEST` 等） |
| 决定说什么内容（`topic` / `content`） | 声称「我已经被枢纽转发过了」（`relayed_by`） |
| 引用一条消息来答复（`reply_to`） | 决定自己在 trace 里的编号（`id`） |

拓扑怎么长、链接给谁不给谁，仍由宿主侧的 `Topology` 与 `MessageBus` 决定。
远端最多只能就「要不要跟我直连」表个态（见 §5.5），而链路预算与 LRU 淘汰
依然在宿主手里 —— 表态不改变预算。

## 2. 传输

- **TCP**，默认 `127.0.0.1`。
- **一次会话一条连接**：宿主 `listen`，对端 `connect`。
- 对端**先连、先发 `hello`**。

最后一条是刻意的：内核会在宿主调用 `accept()` 之前就把连上的连接排进队列，
所以「先 connect、再 accept」不会卡住 —— 这让宿主和对端能在**同一个线程里
交替推进**，于是这一层完全不需要并发，也就没有竞态。

> 明文、无认证、仅环回。这不是疏漏，是当前的边界，见 §10。

## 3. 分帧

**NDJSON**：一帧 = 一行 UTF-8 JSON，以 `\n` 结束。

```
{"t":"think","round":2,"box":[...]}\n
```

规则：

1. 单帧上限 **1 MiB**（`MAX_LINE_BYTES`）。超限即报错，**不许**继续累积缓冲。
2. 空行是**心跳**，跳过，不算帧。
3. 对端在行中间断开（有半截数据但没换行）＝ **协议错误**，不是「本轮到这儿就没了」。
4. 收到不是合法 JSON 的一行 ＝ **协议错误**，不要跳过它继续读下一行。

为什么是 NDJSON 而不是长度前缀的二进制帧？长度前缀更省字节、少一次扫描，
但**调试下限**差一截：出问题时你没法用 `nc` 手搓一条消息发进去看反应。
见 §9。

## 4. 角色与时序

**宿主驱动，对端应答。** 对端从不主动说话 —— 它只在被问到时回答。

```
对端                                宿主
 |                                   |
 |---- hello  (身份 / 职责 / 能力) -->|
 |<--- welcome (名册 / 通讯录 / 枢纽) -|
 |                                   |
 |         ┌── 每一轮，若对端有活 ────┐
 |<--- think  (轮次 / 信箱 / 黑板快照) -|
 |---- say    (我想发这些 / 我还欠着) ->|
 |         └────────────────────────┘
 |                                   |
 |         ┌── 有人想与对端直连 ──────┐
 |<--- link?  (谁 / 为什么)           -|
 |---- link!  (接受 / 拒绝)          ->|
 |         └────────────────────────┘
 |                                   |
 |<--- bye                            -|   任一方都可以发
```

要点：

- 对端**只在 `think` 之后才需要状态**。它没有信箱、没有调度器、没有拓扑 ——
  那些都在宿主那边。它甚至可以完全无状态，每次把上下文扔了。
- `think` 只会发给**有活的**对端（信箱非空，或对端上次声明 `pending: true`）。
  空闲的对端不会空转。
- `link?` 只在**宿主认定这个对端有权表态**时才会出现（见 §5.5）。
- 上面这些往返全部是**同步**的，一次只有一个在飞。

## 5. 帧定义

`t` 是帧类型。所有帧都是 JSON 对象。

### 5.1 `hello`（对端 → 宿主）

```json
{"t":"hello","proto":1,"agent":"deploy","role":"发布平台",
 "owns":["release_meta"],"caps":["accepts_link"]}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `proto` | 是 | 整数协议版本。对不上直接被拒（§8）。 |
| `agent` | 是 | 身份。**必须与宿主为这个座位预留的 id 一致**，否则握手被拒。 |
| `role` | 否 | 人类可读的角色名。 |
| `owns` | 否 | 自报的职责范围（topic 列表）。 |
| `caps` | 否 | 能力声明。未知能力会被整帧拒收 —— 不认识的能力不能默认开启。 |

### 5.2 `welcome`（宿主 → 对端）

```json
{"t":"welcome","proto":1,"session":"s1",
 "agents":["sre","gateway","deploy","ordersvc"],
 "directory":{"release_meta":["deploy"]},
 "hub":null}
```

`directory` 是共享黑板的通讯录只读视图；`hub` 在星型拓扑下是枢纽 id，否则 `null`。

### 5.3 `think`（宿主 → 对端）

```json
{"t":"think","round":2,
 "me":{"id":"deploy","role":"发布平台"},
 "box":[{"id":"m00007","from":"dba","to":["deploy"],"kind":"QUERY",
         "topic":"release_meta","content":"请核实发布记录","reply_to":null}],
 "directory":{"release_meta":["deploy"]},
 "facts":{"slow_query":"order_items 全表扫描"}}
```

- `box` 是本轮这个对端收到的全部消息。
- **`relay_to` 会在需要时出现**：说明宿主认定这个对端是枢纽，这条消息要靠它代投。
- `facts` / `directory` 是黑板的**只读快照**，有长度上限 —— 不会随运行时长无限增长。

### 5.4 `say`（对端 → 宿主）

```json
{"t":"say","pending":false,
 "msgs":[{"to":["dba"],"kind":"ANSWER","topic":"release_meta",
          "content":"v2.31 不含任何 DDL","reply_to":"m00007"}]}
```

`msgs` 里每条报文**只允许**出现这些字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `to` | **字符串数组** | 收件人。广播要显式写 `["*"]`。 |
| `kind` | 字符串 | 必须在数据面白名单内：`TASK` `QUERY` `ANSWER` `FINDING` `FINAL` `INFORM`。 |
| `topic` | 非空字符串 | |
| `content` | 字符串 | |
| `reply_to` | 字符串或 `null` | 引用一条消息，让它能沿原路回去。 |
| `relay_to` | 字符串或 `null` | **仅当对端就是枢纽**时才允许出现。见 §6。 |

`pending`（可选，默认 `false`）＝「我还有未了之事，别判定收敛」。
缺了它，「问了没人答、想过一会儿再问」这个场景在线协议上就表达不出来，
系统会在重试窗口打开之前就宣布收敛。

### 5.5 `link?` / `link!`（建链协商）

```json
{"t":"link?","from":"dba","topic":"release_meta","origin_kind":"QUERY"}
{"t":"link!","ok":true}
```

只有当对端在 `hello.caps` 里声明了 `accepts_link` 时，宿主才会真的把这个问题
转给它。**没声明**的话，宿主按默认策略代答（问的是它负责的 topic、或对方在
向它汇报 → 接受；其余拒绝），对端根本看不到这一帧。

`origin_kind` 携带的是「它在替哪种业务消息谈链路」—— 没有它，接收方分不清
「这是业务提问」还是「这是在汇报结论」，会拒掉本该接受的连接。

### 5.6 `error`（宿主 → 对端）

```json
{"t":"error","reason":"msgs[0] 的 to 必须是字符串数组，收到 str"}
```

宿主拒收一帧时，**先把原因说出来再断开**。不告而别会让人去猜是网络问题
还是自己写错了 —— 而这恰恰是本项目最想消除的体验。

### 5.7 `bye`

```json
{"t":"bye"}
```

双向。收到就收工，不需要回复。

## 6. 字段归属：权限边界

这一节是整个协议里**唯一不能商量**的部分。

远端提交的每条报文，字段分三类：

| 类别 | 字段 | 宿主如何处理 |
|---|---|---|
| **可写** | `to` `kind` `topic` `content` `reply_to` | 照单收下 |
| **拒收** | `sender` `relayed_by` `origin_kind` | **整帧拒收**（`PermissionDenied`） |
| **忽略** | `id` `msg_id` `hop` `path` `ts` | 静默覆盖成框架自己算的值 |
| **条件可写** | `relay_to` | 仅当对端身份是枢纽；且 `relayed_by` 仍由宿主按身份**推出**，绝不取自线上 |

为什么不是「一律忽略」？因为这三类的失败方式不一样：

- **提权字段若静默忽略，对端会以为自己成功了**，然后对着一个永远不生效的
  行为查半天。这类「静止的失败」正是这个项目一整节（README §9）在追杀的东西。
- 其中最危险的是 `relayed_by`。README §9 第 1 条已经证明：只要它等于枢纽 id，
  报文就**直接绕过拓扑投递**。让远端能填它，等于给它开了一条拓扑旁路 ——
  关于「谁能跟谁说话」的整个实验都会因此失效。
- 反过来，`id` / `hop` / `path` 这类字段宿主本来就会覆盖。对端带上只是冗余
  （「把收到的报文原样回传」是很自然的写法），拒收反而会误伤正常实现。

**永不 `tuple()` 一个字符串。** `tuple("audit")` 会得到
`('a','u','d','i','t')` —— 五个幽灵收件人，而真正该收到消息的那个一个字节
都没拿到。无异常、无日志，只表现为「他们没回我」。所以 `to` **必须已经是
数组**；写成单个字符串一律拒收，不替它猜。

## 7. 错误处理

**线上从严，不做静默降级。**

LLM 边界的处理是「解析失败 → 这轮什么都不发」，因为模型输出本来就潦草，
丢掉一轮是优雅的。**线上不一样**：对端是有人照着规范写出来的**程序**，
它的输出不合规说明那个程序有 bug，而一个带原因的响亮报错才是作者需要的。

宿主收到不合规的 `say` 时：抛出异常 → 由运行时的故障隔离接住 →

- 原因进 `RunResult.faults`（带 agent 名与 traceback）；
- 该批**在途消息进死信队列**，不凭空蒸发；
- 连续出错达到阈值 → 把这个成员摘除，其余成员继续跑；
- 该成员最终在 `RunResult.describe_outcome()` 里被点名。

也就是说，对端写得不对**不会静默降级**，会变成一条看得见的故障记录。

## 8. 版本协商

`hello.proto` 与宿主的 `PROTO_VERSION` 不一致 → 宿主回一帧 `error` 并断开。
**不做「尽力兼容」** —— 一个含糊兼容的协议，最后会变成每个人都只测自己那一半。

## 9. 一个最小实现

对端其实很小。下面是骨架（伪代码，任意语言）：

```text
connect(host, port)
send  {"t":"hello","proto":1,"agent":MY_ID,"owns":MY_TOPICS}
loop:
  frame = readline_as_json()
  switch frame.t:
    "welcome": remember roster
    "think":   send {"t":"say","msgs":decide(frame.box),"pending":false}
    "link?":   send {"t":"link!","ok":should_accept(frame)}
    "bye":     exit 0
    default:   exit 3        # 不认识的帧 = 协议违规，别装作没看见
```

**调试技巧**：因为分帧是 NDJSON，你可以手搓一条消息直接灌进去。

Linux / macOS（`nc` 自带）：

```bash
printf '%s\n' '{"t":"hello","proto":1,"agent":"probe","owns":[]}' | nc 127.0.0.1 8912
```

Windows 与没有 `nc` 的环境（`nc` 是 netcat 的一部分，**不是**操作系统的标配：

```bash
python -c "import socket,sys;s=socket.create_connection(('127.0.0.1',8912));s.sendall(sys.argv[1].encode()+b'\n');print(s.recv(4096).decode())" '{"t":"hello","proto":1,"agent":"probe","owns":[]}'
```

宿主会回一帧 `welcome` —— 或者一帧 `error` 告诉你哪里不对。实测的三种反应：

```text
合法 hello        {"t":"welcome","proto":1,"session":"s1","agents":[...],"directory":{...},"hub":null}
座位被占          {"t":"error","reason":"对端自称 'probe'，但这个座位属于 'dba'"}
版本对不上        {"t":"error","reason":"协议版本不一致：对端 9，本端 1。不做尽力兼容 —— 请让对端按 PROTOCOL.md 对齐版本号。"}
```

注意最后一种：**拒绝的理由会原样说给你听**，而不是让你去猜是网络问题还是自己写错了。
这是选择 NDJSON 换来的东西，非常值。

参考实现见 [`tools/peer_agent.mjs`](../tools/peer_agent.mjs)（Node，零 npm 依赖，
约 200 行）。它同时是「怎么给协议加一个第三语言实现」的样板。

## 10. 已知限制（请先读这一节）

- ⚠️ **这是研究原型，不是生产级传输。** 明文、无 TLS、无认证、无流量控制。
  身份只由「谁先连上这个座位」决定 —— 局域网里任何进程都能冒充。
  请只在环回或完全可控的网络里用。
- **一次会话一个对端。** 多对端是明确未实现的（宿主侧的 `accept` 是同步阻塞的）。
- **宿主的调度仍是单线程轮转。** 线协议这一层没有引入并发 —— 所有往返都是
  同步的，一次只有一个在飞。这换来了「不需要竞态测试」，代价是吞吐。
- **远端大脑是「答所问」级别的参考实现。** 它不会推理、不会追问、不下结论。
  把 `dba` 那种需要顺着线索追问的角色交给它，跑不出根因 —— 这不是协议的
  限制，是参考实现的限制。
- **没有断线重连。** 连接一断，宿主侧会把它记成故障并按阈值摘除该成员。
- **`facts` / `directory` 快照有上限**（64 / 256 项），超出部分不会推给对端。
- **未被验证的部分**：只有 Python ↔ Node 这一对实现互通过。
  「第三种语言也能实现」是**基于规范推断的**，不是已验证的事实 ——
  想让它变成事实，就把第三种实现写出来并加进 `tests/test_interop.py`。
